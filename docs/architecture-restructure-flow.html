Jabhouy target architecture

Two views of the same target. 1 is the workspace: three packages, everything else stays a feature folder in lib/. 2 is what one feature looks like inside — same shape whichever side of that line it lands on.

01Workspace modules

The doc extracts exactly three packages and rejects a package per feature: eight pubspecs and cross-package codegen at 20k lines buys nothing. jabhouy_shop is the single experiment. A layer may import anything below it, never above — and because core and sync are real packages, that is a compile error rather than a review comment.

02Inside one feature

Every feature gets this shape — jabhouy_shop as a package, loaner and income as folders in lib/. The seam is the repository: ui/ never touches Drift or ApiService, and every write leaves through one outbox instead of four syncPendingChanges() clones.

Why three packages, not eight

  • core and sync are packaged so "no app imports" and "no Flutter" become compile errors
  • shop is packaged as the experiment — one answer beats eight pubspecs
  • Everything else stays a folder in lib/, layered but not extracted
  • lmsmobileapp gets clean layering at 8.6× the size with zero packages
  • Dart 3.13.1 resolves workspace: natively — no melos

What the outbox fixes

  • attemptCount + nextAttemptAt make a failed push retryable, not terminal
  • dependsOnLocalId orders a ShopItem after its offline Category
  • Delete results are checked, not hardcoded to success
  • UUID localId kills the 16.7-minute ID collision
  • Reconciliation runs in one Drift transaction — no delete-then-insert gap

Still open in review

  • Where do Drift tables live once packages split (phase 5 codegen risk)?
